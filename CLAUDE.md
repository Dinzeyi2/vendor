# Cognex API

FastAPI service that runs open-source algorithms behind one endpoint, `POST /v1/execute`, with
customer API keys and prepaid credits. Deployed on Railway from `main` of github.com/Dinzeyi2/vendor
(https://vendor-production-41cd558f.up.railway.app); a push to `main` redeploys (8-13 min; watch
`/health` for the commit).

## Adding a GitHub repo

When the user says **"Add this GitHub repo to Cognex: <URL>"**, follow
`.claude/skills/add-github-repo/SKILL.md`. Capabilities are added only through manifests in
`app/capabilities/` plus adapters in `app/ops/`, never by editing the router or registry.

## Customer GitHub imports (self-service)

Signed-in customers paste a public GitHub URL. Cognex then fetches the repo, checks its license
and analyzes it, installs dependencies (wheels only), and discovers the algorithm and tests it
in the sandbox. Finally it verifies the operation with a real `/v1/execute` call, and the import
is Ready, private to that customer.

- `app/imports/` holds the pipeline:
  - `jobs.py`: queue, worker, stages, failure codes
  - `github.py`, `licensing.py`, `packaging.py`, `installer.py`: trusted steps that never run repo code
  - `sandbox.py` + `sandbox_boot.py` + `runner.py`: isolated execution
  - `private.py`: per-customer capabilities
- The endpoints live in `app/imports_api.py`.
- **Untrusted code runs only in the sandbox:** a random unprivileged uid, an empty environment,
  seccomp blocking network sockets, and resource limits. Strict mode needs Linux and root, which
  Railway provides. Check it with `GET /v1/admin/imports/sandbox-selftest` (operator key).
- `COGNEX_SANDBOX=insecure-dev` is for tests with this repo's own fixtures only. Never use it
  to run third-party code on a developer machine.
- Imports are never added to the global registry or catalog. Keep it that way: they're looked up
  per caller in `app/imports/private.py`.
- **Published imports:** the operator adds a repo with `POST /v1/admin/imports` (operator key,
  owner `cognex-operator`) plus `"publish": {"name": "category.action", "summary": ...}`, or later
  with `POST /v1/admin/imports/{id}/publish`. Once Ready it is callable by every API key through
  `/v1/execute`, listed in `/v1/operations`, and attributed on `/v1/open-source`
  (`private.published()`). Only operator-owned imports can be published; customer imports stay
  private. Published names follow the public naming rule (no library/GitHub names).
  `.../unpublish` removes it. Pass `when_to_use` (and a `summary`) when publishing: both appear in
  discovery.

## Discovery (`GET /v1/operations`)

Built by `app/discovery.py` from the manifests (built-in, published, and the caller's private
imports). Each entry has: purpose, when_to_use, required_inputs, optional_settings, and a working
request_example/response_example. It also has catalog_version, which is the ETag. Every built-in
manifest needs `when_to_use` and the real `example.output`; `verify_capabilities.py` checks both.
`scripts/discovery_test.py [BASE]` runs every published example exactly as written.

## Layout

- `app/capabilities/*.json`: one manifest per operation. It holds:
  - public name and old-name aliases
  - summary, intents and clarifying question
  - input schema, data bindings and example
  - runtime and timeouts
  - license and pinned dependency
- `app/manifests.py`: the manifest format (`MANIFEST_SCHEMA`) and loader.
- `app/registry.py` builds the operations and worker processes from the manifests.
- `app/catalog.py` holds the public names and aliases.
- `app/router.py`: plain-English routing (`request` + `data` → one registered operation, or a
  question). It's deterministic, makes no model calls, and contains no operation names.
- `app/capability_checks.py` + `scripts/verify_capabilities.py`: the checks every manifest must
  pass; `--live` also runs the examples against a server.
- `app/main.py`: endpoints. A task is either `operation` + `inputs` or `request` + `data`.
  Tasks are routed and validated before credits are reserved.
- `app/ops/*_ops.py`: adapters (`OPERATIONS = {internal_name: fn}`).
- `app/worker_main.py`, `app/workers.py`: the worker subprocess protocol (JSON lines on a private fd).
- `app/billing.py`, `app/billing_api.py`, `app/accounts.py`, `app/account_api.py`, `app/migrations.py`:
  credits, keys, usage and versioned Postgres migrations.
- Docs and licensing:
  - `docs/cognex-api-guide.md` (published in Lovable) and `docs/open-source-acknowledgements.md`
    (generated by `scripts/build_open_source_page.py`)
  - `licenses/` and `THIRD_PARTY_NOTICES.md`
- `vendor/`: the user's reference copies of the original repos. Never modify it.

## Rules

- Never print, log or commit secrets. `.env` is gitignored; the user edits it with `! notepad .env`.
  Scripts read keys from `.env` without printing them.
- Never trust a customer ID from a browser: website-backend auth uses `WEBSITE_BACKEND_SECRET`
  + `X-Customer-Id`. Credit grants use their own `CREDITS_GRANT_SECRET`.
- Public names, catalog, guide and examples never mention library or GitHub project names; old
  names stay working as aliases. Attribution lives only on the open-source page.
- Commit and push only when the user explicitly asks; branch off `main` only if asked.
- Production `BILLING_MODE` is the user's decision; don't change Railway variables.

## Tests

- `.venv/Scripts/python -m pytest -q tests`: the Postgres tests use pgserver in `.runtimes/pgdata`.
- `scripts/smoke_test.py [BASE]` (`API_KEY`): every operation, both names, and failure isolation.
- `scripts/guide_test.py [BASE]` (`COGNEX_API_KEY`): runs every example in the guide exactly as written.
- `scripts/verify_capabilities.py [--live BASE]`: the manifest checks.
